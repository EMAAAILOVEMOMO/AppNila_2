01

Control de versiones

Un sistema de control de versiones (VCS) registra cada cambio hecho a los archivos de un proyecto, quién lo hizo y cuándo, de modo que siempre puedes volver a un estado anterior o trabajar en equipo sin pisarte el código.

Tipos de sistemas

  • Locales: guardan versiones en la misma computadora (por ejemplo RCS). Simples, pero sin trabajo en equipo.
  • Centralizados (CVCS): un servidor central tiene la historia completa (SVN, CVS). Todos se conectan a él.
  • Distribuidos (DVCS): cada persona clona el repositorio completo con toda su historia (Git, Mercurial).
VENTAJAS · DISTRIBUIDOTrabajas sin conexión, ramas baratas y rápidas, cada clon es una copia de seguridad.
DESVENTAJAS · DISTRIBUIDOCurva de aprendizaje más alta y archivos binarios grandes pesan en el repositorio.
VENTAJAS · CENTRALIZADOModelo fácil de entender, control de acceso y bloqueo de archivos sencillo.
DESVENTAJAS · CENTRALIZADOSi cae el servidor nadie puede guardar cambios; ramas más lentas y costosas.

Cómo funciona Git

  • Directorio de trabajo: editas tus archivos.
  • Área de preparación (staging): eliges qué cambios entrarán con git add.
  • Repositorio: git commit guarda una instantánea con mensaje.
  • Remoto: git push la comparte en GitHub o GitLab.

Rastreo y gestión de cambios

  • git log y git diff muestran qué cambió.
  • git blame indica quién tocó cada línea.
  • Las ramas aíslan funciones nuevas; el merge o pull request las integra con revisión.
  • Las etiquetas marcan versiones publicadas (v1.4.0).

Ejemplo: flujo con una rama

terminalbash
# crear una rama para la nueva pantalla de login
git switch -c feature/login
# ...editar archivos en Android Studio...
git add app/src/main/java/.../LoginActivity.kt
git commit -m "Agrega pantalla de login"
git push -u origin feature/login
# abrir un Pull Request, revisar y fusionar a main
git switch main && git pull
git merge feature/login

02

Persistencia y acceso a datos

Persistir es guardar información para que sobreviva al cierre de la app o al reinicio del teléfono. Según el tipo de dato y quién debe verlo, se elige entre archivos, preferencias, base de datos local o un servicio remoto.

Formas de persistencia

Archivos. Almacenamiento interno (privado de la app) o externo (compartido). Ideal para imágenes, PDF, JSON o registros.

Preferencias. Pares clave–valor con SharedPreferences o DataStore: ajustes, sesión, tema.

Base de datos local. SQLite (a través de Room) para datos estructurados y consultas.

Remota vía servicios web. API REST o Firebase; los datos viven en un servidor y se sincronizan.

Qué se guarda en cada una

  • archivos binarios, multimedia, texto, JSON.
  • preferencias booleanos, números, cadenas, conjuntos pequeños.
  • SQLite / Room tablas relacionadas: usuarios, pedidos, mensajes.
  • remoto datos compartidos entre usuarios y dispositivos.

Mecanismos de acceso

  • Biblioteca de clases del SDK: File, SharedPreferences, ContentResolver.
  • Clases SQLite: SQLiteOpenHelper y SQLiteDatabase con SQL escrito a mano.
  • Mapeo objeto-relacional (ORM): Room convierte clases Kotlin en tablas y ofrece consultas verificadas al compilar.

Autenticación y servicios web

  • El usuario envía credenciales por HTTPS.
  • El servidor devuelve un token (JWT u OAuth 2.0).
  • La app lo guarda de forma segura y lo manda en el encabezado Authorization.
  • Con Retrofit se consume el JSON y se convierte a objetos.

Ejemplo: tabla con Room

Tarea.ktkotlin
@Entity(tableName = "tareas")
data class Tarea(
    @PrimaryKey(autoGenerate = true) val id: Int = 0,
    val titulo: String,
    val hecha: Boolean = false
)

@Dao
interface TareaDao {
    @Insert  suspend fun agregar(t: Tarea)
    @Query("SELECT * FROM tareas WHERE hecha = 0")
    fun pendientes(): Flow<List<Tarea>>
}

03

Gestión de sensores

Los sensores son componentes de hardware que miden el entorno o el movimiento del teléfono y entregan esos valores a la app. Con ellos una aplicación puede contar pasos, girar el mapa, ajustar el brillo o detectar una caída.

Tipos de sensores en dispositivos móviles

Movimiento acelerómetro, giroscopio, vector de rotación, contador de pasos.

Entorno luz ambiental, presión (barómetro), temperatura, humedad.

Posición magnetómetro (brújula), proximidad y GPS.

Proceso de gestión

  • Habilitación: obtener SensorManager y verificar que el sensor exista (y pedir permiso si es sensible).
  • Obtención: registrar un listener con la frecuencia de muestreo deseada.
  • Procesamiento: recibir los valores, filtrarlos (por ejemplo, filtro paso-bajo) y actuar.
  • Liberación: dar de baja el listener al pausar la app para ahorrar batería.

Buenas prácticas

  • Registrar en onResume() y liberar en onPause().
  • Usar la frecuencia más baja que resuelva el caso.
  • Comprobar siempre si getDefaultSensor() devuelve null: no todos los equipos tienen todos los sensores.

Ejemplo: leer el acelerómetro

MainActivity.ktkotlin
class MainActivity : AppCompatActivity(), SensorEventListener {
    private lateinit var sm: SensorManager
    private var acel: Sensor? = null

    override fun onCreate(b: Bundle?) {
        super.onCreate(b)
        sm = getSystemService(SENSOR_SERVICE) as SensorManager
        acel = sm.getDefaultSensor(Sensor.TYPE_ACCELEROMETER)
    }
    override fun onResume() {
        super.onResume()
        acel?.let { sm.registerListener(this, it, SensorManager.SENSOR_DELAY_UI) }
    }
    override fun onPause() { super.onPause(); sm.unregisterListener(this) }

    override fun onSensorChanged(e: SensorEvent) {
        val (x, y, z) = e.values
        // procesar: filtrar, calcular magnitud, detectar sacudida...
    }
    override fun onAccuracyChanged(s: Sensor?, a: Int) {}
}

04

Uso de recursos multimedia

Los recursos multimedia son los contenidos visuales y sonoros de una app: imágenes, audio, video y animaciones. Se almacenan dentro del proyecto o se descargan, y se muestran con componentes especializados.

Tipos aplicables

  • Imágenes: PNG, JPG, WebP y vectores (VectorDrawable, SVG).
  • Audio: efectos cortos y música (MP3, OGG, AAC).
  • Video: clips locales o en streaming (MP4, HLS).
  • Animaciones: de propiedades, de cuadros, Lottie.
  • Elementos visuales dinámicos: dibujo con Canvas, gráficos y transiciones.

Estructura del proyecto

app/src/main/
├─ res/
│  ├─ drawable/   # imágenes y vectores
│  ├─ mipmap/     # íconos de la app
│  ├─ raw/        # audio y video locales
│  ├─ anim/       # animaciones XML
│  └─ font/       # tipografías
└─ assets/        # archivos sin procesar

Componentes de software

ImageViewGlide / Coil mostrar y cargar imágenes con caché.

MediaPlayerSoundPool reproducir música y efectos de sonido.

VideoViewMedia3 / ExoPlayer reproducir video local o en streaming.

ObjectAnimatorLottieCanvas animar y dibujar elementos dinámicos.

Ejemplo: reproducir un sonido de res/raw

Sonido.ktkotlin
val player = MediaPlayer.create(this, R.raw.click)
player.start()
player.setOnCompletionListener { it.release() }  // liberar memoria al terminar

05

Servicios y notificaciones

Los servicios permiten que la app haga trabajo sin pantalla visible, y las notificaciones avisan al usuario de eventos importantes aunque la app esté cerrada. Juntos mantienen viva la experiencia fuera de la pantalla principal.

Tareas en segundo plano

Son trabajos que se ejecutan sin interfaz: sincronizar datos, subir fotos, descargar archivos o reproducir música.

  • Corrutinas / hilos: trabajo corto mientras la app está abierta.
  • WorkManager: tareas diferibles y garantizadas, aun si se reinicia el equipo.
  • Foreground Service: trabajo continuo y visible (música, navegación).

Tratamiento de notificaciones

  • Crear un canal de notificación (Android 8+).
  • Pedir el permiso POST_NOTIFICATIONS (Android 13+).
  • Construir el mensaje con NotificationCompat.
  • Mostrarlo con NotificationManagerCompat y definir qué abre al tocarlo.

Proveedores de contenido

Un ContentProvider expone datos de una app a otras mediante URIs y los accede un ContentResolver. Así funcionan los contactos, el calendario o la galería.

Servicios de cómputo en la nube

  • Firebase: autenticación, Firestore, almacenamiento y mensajería push (FCM).
  • AWS Amplify y Google Cloud: APIs, funciones sin servidor y almacenamiento.
  • Ventaja: escalan sin que administres servidores.

Ejemplo: mostrar una notificación

Notificar.ktkotlin
val noti = NotificationCompat.Builder(this, "avisos")
    .setSmallIcon(R.drawable.ic_campana)
    .setContentTitle("Recordatorio")
    .setContentText("Tienes una tarea pendiente")
    .setPriority(NotificationCompat.PRIORITY_DEFAULT)
    .setAutoCancel(true)
    .build()
NotificationManagerCompat.from(this).notify(1, noti)

Librerías y toolkits para desarrollo móvil

Nadie programa todo desde cero: se reutiliza código ya probado. La diferencia está en el alcance: una librería resuelve una tarea concreta y un toolkit aporta un conjunto completo de herramientas y componentes.

Librería

Colección de funciones y clases que tu código llama cuando las necesita. Tú controlas el flujo del programa.

RetrofitGlideRoomMoshi

Toolkit

Conjunto de herramientas, componentes de interfaz y reglas que forman la base sobre la que construyes la app completa.

Android SDKJetpack ComposeFlutterSwiftUI

Librerías especializadas por tarea

  • Red y APIs: Retrofit, OkHttp, Ktor.
  • Imágenes: Glide, Coil, Picasso.
  • Datos locales: Room, DataStore, Realm.
  • Inyección de dependencias: Hilt, Koin.
  • Pruebas: JUnit, Espresso, MockK.

Diferencias entre toolkits aplicables

NATIVOS · ANDROID / iOSJetpack Compose (Kotlin) y SwiftUI: máximo rendimiento y acceso total al hardware, pero un código por plataforma.
MULTIPLATAFORMAFlutter (Dart), React Native (JavaScript) y Kotlin Multiplatform: una sola base de código para ambas plataformas.

Depuración y seguridad

Depurar es encontrar, entender y corregir errores del programa. La seguridad busca que la app y los datos del usuario resistan accesos indebidos, filtraciones y manipulación.

Herramientas de depuración

  • Logcat: registro de mensajes y errores en vivo (Log.d, Log.e).
  • Depurador: puntos de interrupción, paso a paso y vigilancia de variables.
  • Layout Inspector: revisa la jerarquía de la interfaz.
  • Profiler: mide CPU, memoria, red y batería.
  • App Inspection: consulta la base de datos de la app en ejecución.
  • ADB: línea de comandos para conectarse al dispositivo.

Prácticas de seguridad

  • Usar siempre HTTPS y validar certificados.
  • Guardar claves y tokens en Android Keystore o almacenamiento cifrado, nunca en texto plano.
  • Pedir solo los permisos estrictamente necesarios.
  • Ofuscar y reducir el código con R8 / ProGuard.
  • Validar toda entrada del usuario y de la red.

Ejemplo: depurar con Logcat

Registro.ktkotlin
private const val TAG = "Login"

Log.d(TAG, "Intento de inicio de sesión: usuario=$usuario")
try {
    repositorio.entrar(usuario, clave)
} catch (e: IOException) {
    Log.e(TAG, "Fallo de red", e)   // aparece en rojo en Logcat
}
// Nunca registres contraseñas ni tokens.
